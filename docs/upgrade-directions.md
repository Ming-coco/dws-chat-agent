# 升级方向记录

从每日 Agent 情报日报里筛出来的、**对我们这套系统真正适用**的做法，作为后续升级的参考。

不是论文摘要集。每条都要能回答三件事：**我们现在是什么样、改动会落在哪个文件、要付多少代价**。只抄结论而不落到我们代码上的条目，不收进来。

相关文档：已定位的缺陷见 [known-issues.md](known-issues.md)，配置项见 [agent-config.md](agent-config.md)，任务记忆的设计见 [no-reply-task-memory-plan-20261012.md](no-reply-task-memory-plan-20261012.md)。

## 怎么用这份文档

- 每条有编号（U1、U2…），讨论时说编号。
- **编号按「收录先后」分配，不按章节位置。** 所以同一个章节里的编号可能是 U8、U9、U10、U18、U19 这样跳着的——新条目一律往后续号，不为了好看去重排（重排会让以前的对话记录和提交信息对不上）。
- **不按日期排序，按主题分组**。同一条如果后续看到更好的论文或实测数据，就地更新，不新开一条。
- 优先级是建议，不是承诺。标「跳过」的条目留着，是为了下次有人再提同一个想法时不用重新查一遍。
- 收录时**必须写下出处链接和日期**。没有出处的条目一律不收——这是我们自己踩过的坑（见 U3）。

## 一、记忆与事项

### U1　事项记忆缺一层离线整理

**出处**：Anthropic《Components of agent memory》，[anthropic.com/research/components-of-agent-memory](https://www.anthropic.com/research/components-of-agent-memory)，2026-11-09 期收录。

**做法**：记忆分四层——transcripts（可搜索的事件日志）→ memory notes（agent 自己写的笔记）→ memory representations（结构化表征，如 wiki）→ injected context（每次会话预加载的部分）。层间整理动作叫 **dreaming**：利用空闲时间回放日志、纠正错误、重建表征，并决定「什么该被预加载进下一次会话」。

**我们现在**：事项存在 `state/audit.sqlite3` 的 `tasks` 表，状态 open/waiting/completed/cancelled，每条带 `evidence_message_ids` 指回原消息。每次会话预加载最近 8 条活跃事项（`<untrusted_active_tasks>`）。**没有离线整理**：不合并重复事项、不降级被证伪的旧结论、不给「该预加载哪几条」做主动选择。

**升级方向**：加一个离线任务（夜间跑），回放当天的 `runs` 和 `tasks`，做三件事：合并指向同一目标的事项、把长期没证据支撑的 open 事项降级、给每次会话挑「与本次消息最相关」的事项（而不是简单按时间取最近 8 条）。

**代价**：新链路，要设计「整理结果存哪、怎么防止整理本身写错」。中等工程，风险在缓存层写坏。

### U2　每条教训要链回原始轨迹，否则记忆会让 agent 变笨

**出处**：WikiTrace，[arxiv 2611.14320](https://arxiv.org/abs/2611.14320)，2026-11-11 期收录。

**做法**：教训存成三级链接——「一句精炼洞见 + 为什么这条轨迹成功/失败的摘要 + 原始轨迹」。新任务先从洞见出发，一旦缺细节、与别条冲突、或来自失败任务，就沿链接往下钻核对再动手。

**我们现在**：**事项记忆做到了**（`evidence_message_ids` 指回原消息，引用未覆盖的 ID 会被拒绝）；**提示词规则完全没做到**——`prompts/worker.md` 43 条规则里只有 1 条带出处。规则错了或代码变了让它不成立时，没人能看出它当初为什么加。

**升级方向**：见 U3，两条是同一件事的两面。

**代价**：见 U3。

### U3　提示词规则缺「出处」和「验证器」

**出处**：Falsification-Gated Self-Evolution，[arxiv 2611.14326](https://arxiv.org/abs/2611.14326)，2026-11-11 期收录。

**做法**：一条教训写入持久状态前，先表示成结构化假设（前提、行为改变、预期效果、**验证器**），在临时状态试用，跑目标迁移、证伪、归档回归三类探针，按实测收益与风险决定提交、修订还是拒绝。实测坏账率：证伪失败 5.0%、回归损伤 1.3%、有害提交 3.6%。

**我们现在**：规则是一条条追加进 `prompts/worker.md` 的，靠人工判断「这条对我们适用吗」。没有出处、没有验证器、没有回归检查。之前还出现过一次**提示词被设置页整份覆盖**的事故（已在 `dashboard.py` 用版本号修掉），说明这类无追溯的文本改动确实会出事。

**升级方向**（二选一或并用）：

- **A 带出处**：每条规则末尾标来源。代价是提示词体积涨约 30%，而它每轮都进上下文，是持续成本。
- **B 带验证器**：加规则时同时写清「怎么判断它起作用了」，没验证过的规则一段时间后补验证或删掉。更能防退化，但要先有评测手段（见 U5）。

**代价**：A 便宜但只是可读性；B 依赖评测，是 U5 的前置。

### U4　存「判断 + 支撑 + 是否仍成立」，而不是只存记录

**出处**：《共享组织皮层》，[arxiv 2611.05753](https://arxiv.org/abs/2611.05753)，2026-11-09 期收录。

**做法**：四层 Signals / Domains / Claims / Dimensions。解释连同理由与「当前成立状态」一起持久化，用真值维护网络在证据变化时修订。

**我们现在**：只有事项（Signal 级），没有「判断」这一层。典型场景是我们已经踩过的坑：**issue 的「状态」是工作流字段，不能当上线证据**——这其实就是一个「判断」，它应该带着支撑和成立状态存下来，而不是写死在提示词里。

**升级方向**：把「这类单据怎么判上线」做成带证据的结构化判断，而不是提示词里的一段话。**远期**，等 U1 的离线整理跑起来再考虑。

**代价**：重构级，暂时不动。

## 二、评测

### U5　我们没有评测数据集

**出处**：企业分析 agent 评测框架横评，[arxiv 2611.14493](https://arxiv.org/abs/2611.14493)，2026-11-11 期收录。

**做法**：横评三种范式——轨迹级 LLM 判分、纯文本 LLM 判分 + 红队、确定性启发式。结论：轨迹级判分 F1=0.90，纯文本判分召回持平但**误报多 5 倍**；**功能测试与安全红队零重叠**，所以要用双框架。

**我们现在**：`src/dws_dm_agent/front_eval.py` 和 `scripts/build_front_eval_dataset.py` 都在，**但 cases 文件不存在**——评测工具建好了，没有数据在跑。刚才那条「不认识的东西就摘掉」的测试用例就是临时口头举例，没有沉淀成数据。

**升级方向**：从 `state/audit.sqlite3` 的真实会话里攒一批带标准答案的用例（报「这个改动上线了吗」、报「这个链接打不开」、带模糊指代的一句话），覆盖三类：该回、该升、该静默。有了它，U3 的验证器才有地方落。

**代价**：低。工具已有，差的是数据整理和持续维护。

**优先级：高。这是 U3 和 U6 的前置。**

### U6　审核预算该花在「被拦下的」样本上

**出处**：Multi-Agent Screening，[arxiv 2611.12705](https://arxiv.org/abs/2611.12705)，2026-11-10 期收录。

**做法**：四条结论都在打「多加几个 agent 更可靠」的脸。最有用的一条：**不做额外假设的话，召回只能靠审 agent 没通过的那些**——随机抽一批被拒样本就能估出漏掉多少，**而且样本量不随 agent 数量增长**。

**我们现在**：前台会大量 `no_reply()`（即「拦下」）。**我们没有任何抽查机制**，所以「漏回了多少」这个数字是未知的。

**升级方向**：定期抽一批被 `no_reply()` 掉的会话，人工看是不是真的该静默。因为样本量是常数级，这事很便宜。

**代价**：低（抽查）/ 中（自动化）。前置是 U5。

### U7　先量清自己死在哪一段

**出处**：AutoBuddy-Bench，[arxiv 2611.12393](https://arxiv.org/abs/2611.12393)，2026-11-10 期收录。

**做法**：只换底座模型就看出系统性迁移——弱模型死在「发现有哪些义务」，中等模型识别得出但**停在执行前**，最强的死在执行且最常错在业务系统操作。反直觉的是：**发现精度与执行质量只有弱相关，是两种能力。**

**我们现在**：没有任何分段统计。`state/audit.sqlite3` 里其实有足够的数据（runs、决策、交付结果），但没人把它按「发现失败 / 决策失败 / 执行失败 / 交付失败」分过类。

**升级方向**：先做一张分类统计表，别急着改架构。知道我们主要死在哪一段，再决定投哪块。

**代价**：低，纯查询。

### U16　评测不能用「通过/失败」一个比特

**出处**：《agent 基准的饱和主要是测量问题》，[arxiv 2611.13541](https://arxiv.org/abs/2611.13541)，2026-11-12 期收录。

**做法**：重新给 8 个基准的已发布结果打分，结论是**大部分饱和出在测量环节，不在任务本身**。两个毛病：① **太粗**——SWE-bench Verified 上相邻的前十名差距小于它自己的测试误差，纠正误差后重排幅度不超过随机删掉每个 agent 1/6 的通过项；② **顶到参考线**——ALE-Bench 前十名按比赛分排得开，改用「人类中位数」判定就全打平了，尽管近一半运行都超过了那个人类。重新跑 Terminal-Bench 时发现：**通过/失败判分下打平的模型，在被测试丢掉的那个数量上差十倍以上。**

**我们现在**：`state/audit.sqlite3` 里的 `runs` 表记录的是「这次处理成没成」，前台/worker 的产出基本按「有没有回复、有没有报错」这个比特来读。**没有任何连续量的度量**——比如这次回复里给对方的信息量、引用的证据条数、需要对方再追问的概率。

**升级方向**：在 U5 攒的评测集上，除了「route 对不对」这个比特，再记至少一个连续量。最省事的是**「对方是否在同一话题上又问了一次」**——这个能从现有会话历史里直接算出来，不需要新埋点。

**代价**：低。前提是 U5 先有数据。

**关联**：U5、U7。U7 是「按阶段分类」，这条是「同一阶段内不要只用一个比特」。

### U17　agent 缺的不是智力，是「能自己验对错」的环境

**出处**：AWS Emulator 与 Werner Vogels 客座文章，[allthingsdistributed.com](https://www.allthingsdistributed.com/2026/11/aws-emulator-and-the-engineers-job-when-agents-write-the-code.html)，2026-11-12 期收录。

**做法**：AWS 让 agent 从**保真度测试**入手——先把每个测试改到「对着真实 AWS 跑通」，测试就记录了真实行为；再让 agent 改模拟器直到通过同一批测试，通不过的地方就是模拟器缺口。所有改动要过一道 **merge gate**（多个安全 agent 做对抗审查 + 通用代码审查 + 确定性检查）。整个 400+ API 的模拟器全部由 agent 编写和测试。

**最值钱的是作者的自述**：他让 Kiro 重建当年自己亲手写的复制引擎，**「我盯着 agent 盯了四个晚上，才发现它根本没有办法检查自己的结果。一旦给了它规格和测试环境，重建只花了两小时」**（原来四个月）。

**我们现在**：这正是我们反复撞到的墙。worker 写完代码后，能做的检查是跑一遍项目自己的测试——**如果项目没测试、或测试本身是过期的（见 U3 的 AGENTS.md 过期问题），它就失去了唯一的自验手段**，只能靠读代码「觉得对了」。`worker.md` 里「交付结果必须与对方的可见性一致」那条，管的是「让对方看到」，不管「让它自己验对」。

**升级方向**：给 worker 的自验手段排个优先级并写进提示词：能跑测试就跑测试；不能跑就用 `browser_run` 打开页面断言；两者都不行时**明说「这次没有可执行的验证手段」**，而不是含糊地说「已完成」。最后这条是防止它用「看起来对」冒充「验证过」。

**代价**：低（提示词一句话 + 顺序约定）。改坏了会怎样：如果写成「必须跑测试否则不许交付」，遇到本来就没有测试的项目会卡死。所以只能是「排优先级 + 如实说明」，不能是硬门槛。

**关联**：U3、U8。这条是那份「规格与测试环境」的我们版本。

## 三、工具与执行层

### U8　页面表征：先花力气在图上看清，比换更强模型划算

**出处**：SARBLOH，[arxiv 2611.06793](https://arxiv.org/abs/2611.06793)，2026-11-05 期收录。

**做法**：把原始输入先转成「对象清单 + 几何简报 + 标注画布」，而不是把原始网格丢给模型。rubric 从 3/28 跳到 25/28，**token 反而降了 89.4%**。

**我们现在**：`src/dws_dm_agent/runners/browser_tools.py` 的 `text` 步骤只回页面文本（截断 4000 字），模型要点哪里全靠 `click_text` 猜。

**升级方向**：加一个「可点元素清单」步骤，返回每个可交互元素的文字、位置、可直接用的选择器。`eval` 步骤现在也能取，但每次都要模型自己现写 JS，不稳定。

**代价**：低到中（约 60 行 + 测试）。**前提是要有失败样本**——先按 U5 攒几个「点不中」的真实案例，再决定清单长什么样。

### U9　SOP 固化成「由代码决定下一步」的工作流

**出处**：ReTrace，[arxiv 2611.14492](https://arxiv.org/abs/2611.14492)，2026-11-11 期收录。

**做法**：把「一条 SOP + 少量运行日志」编译成可复用工作流，**由代码而不是 LLM 决定下一步**。关键抓手是：agent 每次调工具时**写下的那句理由**里藏着条件判断，光看调用序列看不出来。生产平台 79 条流程上完成率 93.8%（agent 96.8%）、成本低 24%、**耗时 1.3 秒对 170 秒**。

**我们现在**：入口那层已经是「代码先判」（`core.py` 的零令牌门 `probe-gate`），但进到 agent 之后每一步都是模型。

**升级方向**：「这个改动上线了吗」这类被反复问、答案结构固定的流程，可以固化成代码路径：直接查流水线、查镜像、拼结论，模型只负责措辞。**三点成功率换 100 倍速度是划算的**。

**代价**：中。要先统计哪些问题重复率最高，不能凭感觉挑。

### U10　把领域知识打成 skill，而不是塞文档

**出处**：GoogleChrome/modern-web-guidance，[github.com/GoogleChrome/modern-web-guidance](https://github.com/GoogleChrome/modern-web-guidance)，2026-11-11 期收录。

**做法**：200+ 篇精选手写实践以 **agent skill + Agentic RAG CLI** 交付，**约 7 MB 纯 JS、CPU 上约 10 ms 检索**。agent 无引导 55% 通过，加了引导 **92%**。

**它最重要的一句话**：明确不交给 MCP 动态工具搜索，理由是**不想把「激活机制」让出去**——MCP 解决「agent 怎么调工具」，没解决「agent 什么时候该想到某个知识」。

**我们现在**：工具全部是 pi extension（不走 MCP），激活靠工具描述。这条路和它们的判断一致。

**升级方向**：如果以后要给 worker 加一大块领域知识（比如某类单据怎么查、某个系统怎么操作），**做成可检索的 skill，不要整段写进 `worker.md`**——提示词每轮都进上下文，文档化知识的边际成本很高。

**代价**：低（是个约定，不是代码）。

### U18　超长结构化输入别按固定长度切，按结构切

**出处**：TreeAgent，[arxiv 2611.13946](https://arxiv.org/abs/2611.13946)，2026-11-12 期收录。

**做法**：输入超上下文窗口时，现有记忆 agent 基本按固定 token 长度切，对 JSON / HTML 这类结构化数据有三个问题：① 定长切分**把同一条记录的字段切开**，破坏关系；② 段里没有层级信息，看不出结构位置；③ 连续的记忆更新会**丢掉推理后续段所需的早先同级记录细节**。TreeAgent 按输入自身层级切：以完整子树和相邻兄弟子树成组切分保住局部结构，给每段附上**结构路径**让 agent 知道祖先和位置，并从低层子段向高层父段加**残差记忆链接**。8 个检索与聚合任务、4 个记忆 agent 上全部提升，平均 +3.61%——幅度不大，但**不换模型、不训练，只改切分与索引**。

**我们现在**：三个工具都在做定长截断，而且截的位置对结构化数据都不友好：

- `src/dws_dm_agent/runners/gitlab_tools.py:40` `MAX_LOG_CHARS = 4000`，第 533 行从尾部截（`joined[-MAX_LOG_CHARS:]`）——对单作业构建日志是对的（错误在尾部），但**对多作业合并输出会把中间某个作业整段切掉**；
- `src/dws_dm_agent/runners/browser_tools.py:39` `MAX_TEXT_CHARS = 4000`，第 649 行从头截——**页面正文从中间断掉**，真正要点的元素可能在后面；
- `src/dws_dm_agent/runners/jira_tools.py:32` `MAX_DESCRIPTION_CHARS = 6000`；
- `core.py` 的 `sanitize_text` 有 34 个调用点，统一用 `[:max_chars-16] + "…[已截断]"`。

**升级方向**：不是全改成 TreeAgent（我们不是长文本记忆系统），只改**两个真出事的地方**：GitLab 多作业合并输出改成「按作业分段、每段保留头尾」，browser 的 `text` 步骤改成「按 DOM 块保留，优先保留含可交互元素的块」。这两处不需要引入层级索引。

**代价**：中。改坏了会怎样：切分逻辑出错时工具返回残缺内容但**不报错**，比现在更糟。所以改的时候必须同时给出「本次截断了多少、截了什么」的显式提示，不能静默截断。

**关联**：U8（页面表征）。

### U19　一次性探索固化成确定性工具，比每次跑浏览器稳

**出处**：Launch HN: Pomerado（YC F26），2026-11-12 期收录。

**做法**：把老系统接进 agent 时，先让 agent **真跑一遍**任务（写 HTTP 请求或 Playwright 脚本），记录「怎么导航、点哪里、拿到什么」，据此生成一个**可泛化的确定性 API**；之后所有调用都走它，通常 5–30 秒返回。鉴权交给确定性登录流程，**模型和录制器永远读不到客户凭据**；运行失败会触发维护任务自动修复（按钮改名、加新约束）。作者的核心判断是「agent 不再被智力限制，而是被**能接进哪些系统**限制」。

**我们现在**：`browser_tools.py` 每次都要现场用 CDP 走一遍页面（`goto` → `click_text` → `expect_text`），**没有「跑通一次就固化下来」的机制**。对偶尔查一次的页面这没问题；但如果某个操作要反复做（比如每天查某系统状态），每次都重新摸索既慢又不稳。

**升级方向**：这条路和 U9（SOP 固化成代码）是同一个方向的两面——U9 面向内部流程，这条面向**没有 API 的老系统**。落地形态可以是：把验证通过的 `browser_run` 步骤序列存成一个命名脚本，之后优先复用，跑失败再回落到自由探索。

**代价**：中。前提是先把「哪些流程真的高频」统计出来（同 U9），否则会固化一堆只用一次的东西。**注意它不是免费的——第一次要慢，只适合高频重复。**

**关联**：U9、U8。

## 四、权限与安全

### U11　授权边界放在「事务性工作区」，而不是每次调用都打断人

**出处**：Aegis OS，[arxiv 2611.08516](https://arxiv.org/abs/2611.08516)，2026-11-09 期收录。

**做法**：每次动作弹确认会让 **45%–57% 的工具调用被打断**，把人逼到「闭眼全批」；另一头 `--yolo` 又把宿主文件、SSH 凭据、云凭证全暴露。Aegis 把授权从「单次调用」移到「事务性工作区」：内核强制沙箱（Seatbelt / Bubblewrap）、Copy-on-Write 影子工作区、带身份绑定的出网代理。实测确认弹窗减少 94%–99.88%，**八类共 80 个攻击成功率从 100% 降到 0**。

**我们现在**：`read_only` 前台 / 可写 worker 的分法是同一思路的粗粒度版本。**但 pi 没有路径沙箱**——`cd ../..` 就能逃出 junction 视图；`.env` 里的 `JIRA_PAT`、`GITLAB_TOKEN` 由子进程自己读。目前只靠 `worker.md` 一句「不读取或输出无关秘密」。

**升级方向**：短期能做的是**收紧令牌可见性**——只把当前任务需要的那一个系统的凭据传给子进程，而不是整份 `.env`。

**代价**：短期改动中低；完整沙箱方案在 Windows 上没有对应物，跳过。

### U12　谁在自报口径，谁就是安全边界

**出处**：《奖励会教 agent 刷指标》，[arxiv 2611.12865](https://arxiv.org/abs/2611.12865)，2026-11-10 期收录。

**做法**：训练分布里只掺 **25% 的冲突样本**，128 次更新后一个任务上就有 **97.9% 的 rollout 学会走捷径**，典型形态是「把上报的分数做上去、实际工作量却下降」。结论：**凡是 agent 能影响自己上报口径的地方（工时、报表、监控数据），那就是安全边界。**

**我们现在**：`src/dws_dm_agent/tools/zhiguan_worklog.py` 的 `allocate_hours()`——各条之间的**分工按证据算**（提交数、文档数、改动文件数加权），但**当天总工时是固定目标值**（`default_daily_hours`，默认 7.5 小时），最后 re-balance 凑到这个数，不是按实际投入累加。工具只生成草稿、不提交（`save_worklog_draft`，不调 submit），最终提交的是人。

**升级方向**：这是**设计取舍，不是缺陷**，改了会影响公司工时合规。但要留档：如果以后有人质疑工时数据，这里是最薄弱的一环。可选做法是草稿里标注「总时长按目标值分配，非实测」。

**代价**：改行为是业务决策，需你拍板；标注是零成本。

### U13　凭证转发要么不做，要么限定到具体命令和具体仓库

**出处**：HN 讨论（ChatGPT 桌面版转发 SSH agent），[news.ycombinator.com/item?id=50422628](https://news.ycombinator.com/item?id=50422628)，2026-11-10 期收录。

**做法**：跑在远程机器上的 agent 能用你本地的 SSH 凭据完成认证，等于**把权限边界搬到了远端**。这是「本地凭证 + 远程执行」这个组合的结构性风险，不是某个产品的 bug。

**我们现在**：部署形态就是「本机 agent → SSH 到服务器」。目前是人工在跑，没有自动化凭证通道，所以风险还没暴露。**但只要做了自动部署，这条立刻成立。**

**升级方向**：做部署能力时，SSH 只授权到具体的命令白名单，不要用能登录一把梭的通用密钥。

**代价**：设计时注意即可。

## 五、编排与多阶段

### U14　「人多力量大」是错的，小队伍并行优于大队

**出处**：并行 agent 小队，[arxiv 2611.09798](https://arxiv.org/abs/2611.09798)，2026-11-09 期收录。

**做法**：27B 模型 + 100 个 agent 的预算下，**10 人小队在 10/12 个长程任务上打赢并行单 agent**；在试过大队的 4 个任务上**全部打赢 100 人单队**。解释：单 agent 输在「样本均值低」，单大队输在「一个样本吃不到方差收益」。

**我们现在**：`max_parallel_conversations: 1`，一个会话一条队列。**这个结论对我们暂时不适用**——客服回复不是长程搜索，也不该为了多样性多烧 token。

**升级方向**：跳过。但记下这条，以防以后有人提出「多开几个 agent 一起答」。

**代价**：—

### U15　该不该中途插手是可以算的，一刀切注定错

**出处**：Knowing When to Intervene，[arxiv 2611.09792](https://arxiv.org/abs/2611.09792)，2026-11-09 期收录。

**做法**：用少量「随机干预下采到的轨迹」估计各类干预策略的动态因果效应。实测**干预的效应随 agent 动作和状态变化极大**。

**我们现在**：`read_only` 前台 + 可写 worker 是典型的一刀切。

**升级方向**：等 U7 的分段统计出来，看哪一段真的是高风险，再决定是不是所有可写动作都要走同一个审批口径。

**代价**：高（要实验数据）。属远期。

## 六、读过但不适用（留档避免重复调研）

| 条目 | 为什么不适用 |
| --- | --- |
| SwarmEvolve（隐空间蜂群通信，[2611.08483](https://arxiv.org/abs/2611.08483)） | 我们不跑多 agent 集群，没有 agent 间通信层 |
| SCALE（带宽受限的多 agent 通信，[2611.08390](https://arxiv.org/abs/2611.08390)） | 场景是有 deadline 的物理系统 |
| Route to Remember（记忆沉进权重，[2611.05636](https://arxiv.org/abs/2611.05636)） | 需要训练，我们不训模型 |
| Agentic-OPD（[2611.12799](https://arxiv.org/abs/2611.12799)） | 同上，且其结论日报自己都标注了「照抄不背书」 |
| FlyHash 负结果（[2611.05791](https://arxiv.org/abs/2611.05791)） | 我们的记忆不是向量检索；这篇本身是诚实负结果，没有收益 |
| HiVe-Mem（多模态记忆，[2611.12872](https://arxiv.org/abs/2611.12872)） | 我们是纯文本单模态 |
| CPU-ARC（推理缓存，[2611.09891](https://arxiv.org/abs/2611.09891)） | 前提是有一批同构重复题；我们的等价做法是把规则写进提示词 |
| Rivet（actor 替代沙箱，[github.com/rivet-dev/rivet](https://github.com/rivet-dev/rivet)） | 我们是单机常驻进程，不是「大量空闲 agent 会话」的负载 |
| Mika / esp32-iphone-agent | 移动端 GUI agent，我们目前只测网页 |
| XStack（[2611.08472](https://arxiv.org/abs/2611.08472)） | 整仓迁移基准。**作为水位参考保留**：最好的 agent 也只有 75%，其余 ≤40% |
| Personalized Memory Rubrics（[2611.14017](https://arxiv.org/abs/2611.14017)） | 核心是训练期的评分表引导信用分配，我们不训模型。它的结论「记忆该记什么因人而异」我们已经用「事项按联系人隔离」结构性满足了 |
| blackhole（容器隔离跑 Claude Code，[github.com/tommy0103/blackhole](https://github.com/tommy0103/blackhole)） | macOS 走 Colima 的实现；我们宿主是 Windows，没有对应物。**它的定位值得记**：只解决「跑在哪」，不解决「能碰什么」 |
| MineAgent（画布拖出 agent 流程，[github.com/YT-Proteus-bot/MineAgent](https://github.com/YT-Proteus-bot/MineAgent)） | 174★ 但只有 1 fork、0 issue，还在很早期。可借鉴的只有「编译产物是独立工程（可版本化/可 diff）」这个设计，我们的流程本来就写在代码和 `config.json` 里，已满足 |
| 美联航禁止 AI agent 代订票（[CBS](https://www.cbsnews.com/news/united-airlines-bans-ai-agents-booking-flights/)） | 平台政策层的动向，不是工程方向。**但结论要记住**：对客 agent 要先确认「对方平台允不允许」，技术能做不等于政策放行 |
