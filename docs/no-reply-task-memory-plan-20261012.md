# dws agent 合法沉默与事项记忆修改方案

日期：2026-10-12

状态：已部分实施（见文末「实施状态」）。本方案替代讨论中的轮次计数、A2A 接入、多层 stale/expired 状态方案。

## 1. 目标与边界

允许人与 agent、两个 agent 正常讨论接口、通知部署、追问结果。模型能够在没有必要继续发送时主动结束本次处理，避免反复确认和客套。

事项记录用于帮助模型理解尚待处理的工作，不是现实世界的权威任务账本。用户可能在线下完成工作，不要求用户回来维护状态。

第一版不引入 A2A，不识别或猜测对方是否为机器人，不计对话轮次，不因任务过期自动发送提醒，不增加定时 LLM 检查。

保留现有资源限流。它只保护运行成本，不用于判断任务完成或消息是否值得回复。

## 2. 用户可见行为

| 场景 | 行为 |
| --- | --- |
| 对方提出问题或请求验证部署 | 按当前请求处理，需要时回复 |
| 对方确认双方已定稿的接口，没有新增问题 | 可以沉默，不再发送“收到”“辛苦了” |
| 对方通知部署完成，而我方此前承诺部署后验证 | 执行已有待办，不能只因是通知而沉默 |
| 对方通知部署完成，没有我方后续动作 | 更新相关事项，可以沉默 |
| 同一条消息确认接口完成，同时提出生产故障 | 关闭有证据完成的事项，处理新故障 |
| 用户接管聊天并自己处理问题 | 暂停 agent 处理，沿用现有人工接管保护，不要求用户维护任务 |
| 用户默默完成工作，系统没有证据 | 不宣称完成。相关旧事项到期后退出默认上下文 |
| 数日后对方再次提出相关问题 | 处理当前消息。必要时查询旧事项，不能因归档而丢弃新消息 |

判断回复的标准是是否有需要传达的新结果、问题、风险、确认或既有承诺。消息包含新信息不等于必须回复；消息没有问号也不等于无需行动。

## 3. no_reply 是正常处理结果

新增零参数工具 `no_reply()`，表示“当前输入已处理，本次不向联系人发送消息”。工具在 front 和 worker 中都可用。

运行结果使用明确的 outcome，至少区分 `reply`、`silent`、`escalate`、`error`、`interrupted`。不要依靠空字符串或相互冲突的布尔值表达沉默。

运行时捕获真实工具调用后产生 `silent`。普通正文里的 `no_reply()` 字样、引用内容、工具返回文本都不能触发控制动作。仅匹配本服务注册的工具名和协议事件。

`silent` 的处理要求如下。

- 作为成功终态，不进入 worker fallback，不生成兜底回复，不记为失败。
- 不写入发送 outbox，不调用正文发送接口，不发送“本次无需回复”的通知。
- 标记本次已消费的输入消息，审计记录 outcome、联系人、输入消息 ID、时间和关联事项变更。
- 只消费当前运行覆盖的消息。终止时并发到达的新消息仍要入队。
- 人工接管、取消和过时运行的检查优先于结果落地。旧运行不能借 silent 覆盖新运行状态。
- 调用 silent 后忽略后续正文，结束该运行；与正常完成、重复事件的处理保持幂等。

空回复仍是失败。模型没有调用工具且没有终稿时，保留现有错误和 fallback 行为。

## 4. 流式展示不能提前破坏沉默

当前系统存在进度和流式卡片。若模型最终 silent，却早已发送卡片或思考片段，就不是真正的本次不发送。

第一版增加运行内的明确展示开关 `begin_response()`。这是交付控制，不是新的业务状态。

- front 不展示中间输出，只在终稿决定发送时进入原发送流程。
- worker 默认不创建对外卡片、不发送进度，内部日志正常保留。
- worker 确定需要对外展示长任务进度时调用 `begin_response()`，再使用现有卡片与进度通道。
- 未调用 begin_response 的普通终稿仍可正常发送，不要求每条短答多调用一次工具。
- begin_response 生效后，不再允许 no_reply 成功。工具返回明确错误，模型须正常收尾；失败仍走错误处理，不能伪装成沉默。
- 提示词规定先判断是否存在需要处理并向对方交付的工作，再开启展示。事项更新或查历史本身不要求开启展示。

运行内展示模式为 `undecided` 或 `responding`。未提交展示的运行可结束为 silent 或 reply；已提交展示的运行不能结束为 silent。

worker 当前具备直接发送附件的能力。沉默只能保证服务管理的输出通道不发送，不能撤销任意 CLI 工具已经发送的内容。第一版要求附件发送前先 begin_response，并将该限制写入验收与提示词。不宣称能拦住任意 shell 外发；集中收口附件发送属于独立工作。

## 5. 事项是带证据的工作记忆

仅为明确的请求、承诺或需要等待后续结果的工作创建事项。闲聊、每条通知和每次确认不单独建 task。

一个事项描述一个可判断的目标。一个联系人可以有多个事项，一条消息也可以涉及多个事项。消息不必强行绑定到某个事项。

业务状态仅保留 `open`、`waiting`、`completed`、`cancelled`。

- open 表示根据最后证据仍有工作。
- waiting 表示等待对方、人工或外部结果，记录具体在等什么。
- completed 要有目标达成的证据。
- cancelled 要有取消或明确替代的证据。

归档独立于业务状态，以 `archived_at` 和 `archive_reason` 表示。人工接管记录为证据事件，不再新增 handed_off、stale、expired 等互相重叠的业务状态。

归档含义固定为“退出默认工作记忆”。归档后的 open 表示最后曾记录为未完成、当前结果未知，不能在回答中称它“现在仍未完成”。

## 6. 人工接管与无声完成

复用现有人工消息识别和人工接管冷却。程序能知道用户发过消息，不能据此判断用户完成了哪个主题。

处理规则如下。

1. 人工接管期间停止自动运行和发送，沿用现有行为。
2. 记录人工接管时间，不把联系人下所有事项批量改成 completed，也不批量归档。
3. 下次允许处理新消息时，给模型提供近期人工消息及其时间。模型按证据判断哪些事项已完成、已取消或仍需处理。
4. 无法关联到具体事项的人工消息不改变事项状态。私人线下操作不可见时，系统保持未知。
5. 有归属证据的接管事项可提前归档并注明人工接管。归档不表示完成。
6. 无人维护的事项最终按无实质更新期限归档，用户无需点完成或清理列表。

不因为冷却结束、收到新消息或旧事项仍为 open，就自动恢复此前执行。每次行动仍依据当前请求、已有授权和最新证据。

## 7. 自动归档

第一版建议未完成事项在连续 2 天没有实质更新后归档。2 天只是可调整的上下文保留默认值，不是已验证的最佳期限，也不是业务截止日期。

配置建议为 `task_memory.inactive_days=2`，同步配置默认值和示例文档。

实质更新仅包括被明确关联的新请求、新结果、状态变化或有证据的人工接管。以下行为不延长保留时间。

- 查询或注入事项快照。
- 联系人聊了其他主题。
- 模型重复写相同摘要。
- no_reply、重复消息或失败重试。

依据 `last_evidence_at` 计算归档时间，而不是泛用的 updated_at。消息时间和服务器记录时间分开保存，重放旧消息不能让旧事项重新变得新鲜。

在服务启动和加载事项快照前执行本地幂等归档，无需单独调度模型。completed 和 cancelled 默认立即退出活跃快照，并可通过查询工具查看。

归档不删除记录，不通知联系人，不自动催办，也不承诺长期提醒。首次版本不提供定时任务能力；用户明确要求未来自动工作时仍走独立调度机制。

## 8. 事项工具与数据

提供两个工具，避免多套重叠接口。

- `task_record(...)` 创建或更新事项。新建时不传 ID，由服务生成；更新必须传当前会话作用域内的真实 ID。
- `task_lookup(...)` 查询当前作用域内的活跃或历史事项。查询不续期，不唤醒归档任务。

task_record 入参包括目标、业务状态、简短证据、关联消息 ID。更新只提交变化。显式恢复归档事项需带 restore 和新的证据，模型不能仅凭同名标题恢复。

最小记录字段如下。

| 字段 | 用途 |
| --- | --- |
| id | 服务生成的事项标识 |
| scope | 本地登录身份、联系人、会话的组合隔离范围 |
| goal | 可判断结果的目标 |
| status | open、waiting、completed、cancelled |
| waiting_on | waiting 时记录等待内容 |
| evidence_summary | 最后观察到的事实，不写推测为事实 |
| evidence_message_ids | 支撑变更的消息引用 |
| last_evidence_at | 最后实质证据时间 |
| created_at、updated_at | 记录管理时间 |
| archived_at、archive_reason | 独立的归档属性 |
| version | 拦截过时运行更新 |

复用现有 SQLite 审计存储，新增事项表与精简变更记录。记录 run_id 和 tool_call_id，用于重复事件幂等。fallback 属于同一输入处理，重复事项调用不得重复创建；同一次运行的重试键与不同输入的合法新事项要区分。

模型提交的证据消息 ID 由服务对照本运行上下文的 message_times 映射（本运行已覆盖消息的 id 与时间戳）校验：只落模型显式引用且存在于映射的 ID，未覆盖的 ID 一律拒绝，不存在“未知 ID 按当前时间落库”的兜底，也不自动附加批内全部消息 ID。last_evidence_at 取被引用消息自身的最新时间戳（引用旧消息，时间就是旧时间），未引用 ID 的新建才用已覆盖消息的最新时间。检查引用存在只证明来源存在，不代表系统机械验证了模型的语义解释。

人工接管发生后，仍在运行的模型不能继续落地任务变更。服务为挂载事项工具的会话在启动前登记运行写入租约，接管/取消/收尾时吊销；变更事务在拿到 SQLite 写锁后校验租约，排队等锁的过期子进程同样被拒绝。冲突时读回最新状态，不能静默覆盖，也不批量改写事项状态。

## 9. 上下文和模型权限

每次模型运行注入消息时间戳、近期对话和有限的活跃事项摘要。事项超过预算时明确提示有省略，并允许 task_lookup 查询，不悄悄丢失。

front 和 worker 都能查看、更新事项，也都能 no_reply。front 只处理能够依据已有对话可靠判断的内容。需要查代码、日志或执行动作时仍 escalate 给 worker。

front 更新的事项会在 worker 启动时重新加载。普通正文不作为数据库写入指令。

事项永远不自动触发执行。程序不根据 open 自动催问，不根据 waiting 自动回复，不根据 completed 丢弃新消息。事项是模型决策的上下文。

提示词必须消除“每条消息必须回复”和“最终必须输出正文”的要求，明确 silent 是合法成功结果。是否沉默由当前输入与相关承诺共同决定，不依据发送者身份、轮次或简单关键词。

## 11. 验收

### 确定性测试

1. front 调用 no_reply 后不启动 worker，不发消息。
2. worker 调用 no_reply 后不启动 fallback，不发消息。
3. 无终稿且未调用 no_reply 仍走原失败路径。
4. silent 不产生流式卡片、进度或空回复，也不产生失败通知。
5. begin_response 后拒绝 silent，正常收尾路径可用。
6. silent 终止时新到消息不丢失，人工接管后旧结果不可发送或改事项。
7. 重复工具事件、进程重启、fallback 重试不重复创建事项。
8. 接口和部署两个主题交错时，变更只影响相关事项。
9. 人工发言不批量标记任务完成。
10. 无声完成场景中，旧事项到期退出快照，业务状态未伪造为 completed。
11. 查询、其他主题聊天和重复摘要不延长事项寿命。
12. 历史消息重放不重置归档期限。
13. 归档后新请求仍处理，查看旧记录不自动恢复旧任务。
14. 不同联系人及不同本地身份的事项无法互读互写。

### 真实模型行为验证

用隔离测试联系人或本地发送替身验证，不向真实同事自动发测试消息。

- 两个 agent 讨论接口，允许实质往返，确认完成后能够沉默。
- 部署通知触发已承诺的验证，不能误判为无需动作。
- 一个主题收尾时另一个主题仍需处理。
- 人工接管后未显式更新状态，旧事项不驱动后续自动催问。
- 请求与纯收尾分别测试，既检查停止互相确认，也检查没有漏掉真正请求。

运行时保证合法沉默不会触发 fallback；模型是否恰当地选择沉默仍需实测。no_reply 不构成数学意义上的循环消除保证，保留现有限流作为独立资源保护。

## 12. 实施顺序与交付边界

先实现 outcome、控制工具和展示延迟，验收 silent 全链路不发送且不回退。再实现事项记忆、人工接管证据与归档。最后跑组合场景和真实模型验证，检查漏回复与重复确认。

本方案没有要求用户手动维护任务，没有按消息轮数结束会话，没有新增自动提醒，也没有把归档视为完成。

## 13. 实施状态（2026-10-12）

第一轮实施范围（最小可用）：

- `no_reply` 只在 pi 运行时（pi-rpc，front 与 worker 都挂载）落地，捕获点为 `tool_execution_end` 且工具执行成功；codex/claude/custom 协议不挂载该工具，保持原有失败路径，空回复不会被误当成沉默。
- silent 作为成功终态：不进 worker fallback、不写发送 outbox、不发送任何通知。为满足「决策前零对外输出」，回复路径的流式卡片进一步推迟到**投递派发时点**（`_dispatch_due_delivery`）：人工接管与补充消息的最终新鲜度检查都通过后才由 `_start_delivery_card` 创建（初始内容即最终回复，含消息编号标记以便回绑 message_id），并绑定投递行供网络重试复用；失败与「补充消息过多」仍在决定点建卡并通知。silent、人工接管、冷却/门控/限流等无投递终态会把会话中残留的处理中卡片（如上次投递重试被补充取消）安全收口成终止态，不悬「处理中」卡片；运行内不对外展示进度或思考（`progress_enabled`/`max_progress_updates` 配置保留解析但暂不生效，待 begin_response 落地后恢复）。
- 事项记忆 `task_record`/`task_lookup` 复用审计 SQLite 新增 `tasks`/`task_changes` 表；状态只有 open/waiting/completed/cancelled，归档独立（archived_at/archive_reason）；按 `last_evidence_at` 满 2 天归档（`task_memory.inactive_days`，非正数关闭）；查询不续期；人工接管不批量改状态；作用域为本地身份+联系人+会话组合隔离；同一 (run_id, tool_call_id) 重复事件幂等。
- 幂等收据与事项变更在同一事务（`BEGIN IMMEDIATE`）内落地：收据命中直接重放已存响应，否则变更与收据一起提交或一起回滚，进程崩溃不会出现「变更已生效但收据缺失」导致重放重复建事项，也消除了「先查收据再变更」两步之间的并发窗口。
- 更新是部分提交：未提交的字段保持原值（status 不会回落到 open）；`waiting_on` 传空串显式清空，显式改到非 waiting 状态时自动清空；重复提交相同内容视为无实质变化，不刷新 `last_evidence_at`、不递增版本，不延长保留期。
- steer 进补充消息后，服务原子重写会话目录的 `task-context.json`（环境变量在 pi 进程启动后不可改，故经 `DWS_TASK_CONTEXT_FILE` 传路径），`task_tools.py` 每次调用优先读它；文件缺失或损坏时回退环境变量初始快照。上下文的 `message_times`（本运行已覆盖消息的 id -> 时间戳映射，含已 steer 消息）是证据 ID 的唯一校验集与时间戳来源：`evidence_message_ids` 只落模型显式引用且存在于映射的 ID（未知 ID 拒绝，绝无「按当前时间兜底」），`last_evidence_at` 取被引用消息自身的最新时间戳——引用旧消息时间就是旧时间，重复提交相同内容或批内出现无关新消息都不会因此续期；未引用 ID 的新建才用已覆盖消息的最新时间。
- 并发安全：task 更新落到带 `version` 条件的单条 UPDATE（`version = version + 1`），读与写之间发生的并发更新/归档使条件失配，读回最新状态返回 `version_conflict`，不静默覆盖；归档 UPDATE 带 `last_evidence_at`+`version` 条件并递增版本，候选扫描后拿到新证据的事项不会被归档。`last_evidence_at` 只随更新的证据前移，引用旧消息不会把已记录的证据时间回拨。`task_tools.py` 由 pi 扩展按 `python <script>` 直接拉起，内置 src 路径引导后按包绝对导入，不依赖安装方式。
- 运行写入租约（`task_run_leases`）：服务为挂载事项工具的 pi 会话在会话启动前登记租约，人工接管、超时、取消与会话收尾（finally，均幂等）吊销。`apply_task_record` 在 `BEGIN IMMEDIATE` 拿到 SQLite 写锁之后先校验租约：被吊销运行的 `task_tools.py` 子进程——包括早已排队等写锁、接管后才拿到锁的——拒绝落地变更或重放旧收据（`run_revoked`）。接管只拦新写入，不批量改写事项状态。
